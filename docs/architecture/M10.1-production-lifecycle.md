# M10.1.1 — Production Lifecycle Contract

Status: approved implementation contract; M10.1.2, M10.1.3 and M10.1.4 validated on disposable PostgreSQL 18.7; M10.1.5 implementation added, PostgreSQL validation pending
Target: PostgreSQL 16+; FastAPI service layer; Qt Quick client
Prerequisites: M9 platform foundation, M10 inventory/production schema, M11 machine/settings schema

## 1. Purpose and boundaries

This document defines the production batch state machine and the invariants that every production command must enforce. It does not introduce a separate Preparation or Cooling form/stage. Setup data belongs in Settings. Cooling remains a timed sterilization-readiness condition.

The lifecycle is:

`Mixing → Press Baglog → Sterilization → Inoculation → Incubation → Kumbung placement → Reconciliation`

A batch status is a server-owned projection of accepted domain events. Clients must call stage commands; they must never set `production_batches.status` directly.

## 2. Batch statuses

| Status | Meaning | Entry condition |
|---|---|---|
| `draft` | Batch definition is being prepared | Batch created |
| `planned` | Recipe/version, location, unit and plan are validated | Explicit plan command |
| `mixing` | Mixing has started; recipe version is pinned | Start mixing command |
| `press_baglog` | Mixing is completed and the batch is ready for pressing | Complete mixing command |
| `sterilization` | Press output is recorded and awaiting/completing sterilization | Complete press command |
| `inoculation` | Required sterilization run(s) and cooling readiness are satisfied | Start/complete inoculation command |
| `incubation` | Variety allocation is recorded and incubation has started | Start incubation command |
| `ready` | Incubation is complete; output is eligible for kumbung placement | Mark ready command after target time and checks |
| `on_hold` | Operational work is paused; previous active status is preserved in the event | Hold command |
| `closed` | Every produced unit is accounted for by placement, loss, recovery or an approved disposition | Reconciliation command |
| `cancelled` | Batch was cancelled before irreversible operational posting | Cancel command |

`ready` means ready for kumbung placement, not necessarily fully placed. Partial placement is permitted while the batch remains ready. `closed` is terminal.

## 3. Allowed transitions

| From | To | Command |
|---|---|---|
| draft | planned | plan_batch |
| planned | mixing | start_mixing |
| mixing | press_baglog | complete_mixing |
| press_baglog | sterilization | complete_press |
| sterilization | inoculation | complete_inoculation_readiness / start_inoculation |
| inoculation | incubation | complete_inoculation / start_incubation |
| incubation | ready | mark_ready_for_kumbung |
| ready | closed | reconcile_and_close |
| any non-terminal operational status | on_hold | place_on_hold |
| on_hold | preserved prior status | resume_batch |
| draft / planned | cancelled | cancel_batch |

The service must reject every transition not listed above. A transition command is idempotent only when the same command identity/idempotency key has already committed the same result; it must not silently reinterpret a conflicting retry.

Cancellation is allowed only before material consumption or any other irreversible production posting/allocation. Once consumption, press output, sterilization execution, inoculation allocation, placement, loss or recovery has been posted, cancellation is rejected. Correct the operational record through an explicit compensating workflow.

A held batch stores its exact prior status in the hold event metadata. Resume returns only to that status; callers cannot choose an arbitrary resume status. Repeated hold/resume commands are rejected unless they are exact idempotent retries.

## 4. Stage invariants

### 4.1 Mixing

- A batch pins one active recipe version and its unit-conversion snapshots before starting.
- Ingredient requirements are scaled from the selected base ingredient; conversion factors must be explicit and positive.
- Actual material consumption is posted through the existing batch-linked inventory consumption service.
- Material consumption is allowed only while the batch is planned or mixing, matching the database guard in migration 0011.
- Recipe estimated output is planning information only. It does not create finished-goods stock or a production lot.
- Mixing completion moves the batch to `press_baglog`; it does not set actual baglog output.

### 4.2 Press Baglog

- Record at least: quantity processed, good output, rejected quantity, unit, timestamp, operator and optional notes.
- The invariant is `processed_quantity = good_quantity + rejected_quantity` unless an explicitly modelled additional disposition explains the difference.
- `per_baglog_actual` press overhead uses the configured actual processed basis, not only the good output.
- Only good output can become the batch's actual baglog output and be posted as production output to inventory.
- Rejected quantity is recorded as a stage loss with a reason/disposition. It is not silently included in finished stock.
- Output posting and batch/event updates must commit atomically and be protected against duplicate requests.

### 4.3 Sterilization

- A sterilization turn may use multiple active sterilizers and may contain multiple batches.
- Every sterilizer allocation is checked against that machine's capacity in its configured capacity unit.
- The combined turn capacity is the sum of participating sterilizer capacities after explicit unit conversion to a common capacity unit. The total allocation cannot exceed this sum.
- A batch may be split across sterilizer runs; the sum allocated for that batch cannot exceed its eligible pressed quantity.
- A run cannot start if any participating machine is inactive, under maintenance, retired, or already occupied by an overlapping run.
- The service locks the turn, participating sterilizers and affected batches in stable order before validating or writing allocations. Capacity validation must be concurrency-safe. Machine and batch capacity conversions must be explicitly configured and snapshotted; identity conversions are implicit.
- Cycle duration and cooling duration are read from the machine configuration and snapshotted for the run. Planned machine occupancy uses the snapshotted cycle duration; cooling is tracked separately after machine completion. No fixed 24-hour interval is hardcoded.
- Cooling is not a batch status. Inoculation is blocked until the sterilization run is completed and its cooling completion condition is satisfied. Persist `completed_at`, `cooling_completed_at`, and notes.

**M10.1.2 schema foundation:** `sterilization_cycles` groups machine-specific `sterilization_runs` into one shared turn. Each run has a nullable `cycle_id` during the compatibility period; legacy runs remain ungrouped rather than being assigned invented cycles. A partial unique index prevents the same sterilizer from being attached twice to one cycle. The application service must require a cycle for every newly created run and enforce combined capacity under locks.

**M10.1.2.1 press-output integrity:** migration 0014 extends the press-output insert guard. It requires an active `PRESS_BAGLOG` machine in the same production unit as the batch, and the output quantity unit must equal `production_batches.output_unit_id`. The guard validates against tenant-scoped batch and machine records without requiring extra machine-update privileges. Migration 0014 is additive and does not rewrite migration 0013. The user confirmed migration 0014 and its smoke test succeeded on a disposable PostgreSQL 18.7 database.

### 4.4 Inoculation

- One inoculation run may combine eligible quantities from multiple sterilization runs/batches.
- Each allocation references one batch, mushroom variety, quantity/unit and optional seed lot.
- Total allocated quantity per batch cannot exceed the quantity whose sterilization and cooling are complete.
- Seed-lot traceability is optional only when the tenant's configured process policy allows it; when supplied, the seed lot must be active, valid and tenant-owned.
- Allocation quantities must reconcile to the eligible quantity, or the remaining quantity must be explicitly recorded as pending/unallocated. Never silently discard a remainder.
- Completing inoculation creates/updates variety-specific traceability lots without breaking the link to the source batch and sterilization runs.

### 4.5 Incubation

- Incubation duration is captured per record and is configurable; 30 days is not a hardcoded rule.
- `expected_move_at` is derived from the actual start time and the configured duration.
- A batch cannot become `ready` before the target time. Early movement requires an explicit override permission, reason and audit event if the business later approves such a policy.
- Marking ready is an explicit command or scheduled domain command; merely passing the clock does not mutate batch status.

### 4.6 Kumbung placement

- Placement is an append-only signed ledger. Current occupancy is calculated from placements, not a manually editable counter.
- Validate source lot quantity, variety/lot traceability, tenant/location relationship, active kumbung, capacity unit conversion and remaining capacity in one transaction.
- Lock the kumbung and affected lot balances in stable order to prevent concurrent over-placement or overdraw.
- Partial placements and moves are allowed when each movement is balanced and source availability remains non-negative.
- A batch remains `ready` while any output is awaiting placement or explicit disposition.

### 4.7 Loss, recovery and reconciliation

- Every loss records batch, stage, reason, quantity, unit, timestamp, actor and disposition.
- Loss quantity cannot exceed the available quantity at the relevant stage/location.
- Recovery creates a new inventory lot and a new traceable recovery record. It never restores quantity to the source lot.
- Recovery cost is derived from the approved historical-cost policy and captured as a snapshot. Master-price changes cannot rewrite it.
- A batch may close only when its total good output is fully accounted for: placed, permanently lost/discarded, or transferred into an explicitly modelled recovery/rework path.
- Final cost snapshots use actual posted material consumption and approved stage overhead allocations. Finalization is immutable; later corrections use compensating allocations.

## 5. Cross-cutting invariants

1. Every command is tenant-scoped and permission-checked from authenticated membership; a client-supplied tenant ID is never authorization.
2. Module entitlement is checked for every operational command.
3. Every status transition appends one immutable `production_batch_events` record in the same transaction as the state update.
4. No direct status updates from UI/API generic CRUD endpoints.
5. Every command uses transaction-scoped idempotency and row/advisory locks for the batch and affected resources.
6. Inventory changes happen only through posted inventory documents and immutable ledger entries.
7. Machine, recipe, unit conversion, duration and cost inputs used by a posted operation are snapshotted.
8. Tenant composite foreign keys and forced RLS remain mandatory.
9. Audit actor, occurrence time and reason are captured for operational changes.
10. A failed command leaves no partial state, ledger, allocation, or event writes.

## 6. M10.1.3 transition service

`src/app/backend/services/production_lifecycle.py` exposes `transition_production_batch`. It owns the batch status projection and appends one immutable `production_batch_events` row per accepted command. The caller supplies the authenticated actor and tenant context, checks the tenant permission, and commits or rolls back the surrounding SQLAlchemy transaction. The user confirmed migration 0015, its smoke test, and the lifecycle integration test (runtime non-owner role) passed on a disposable PostgreSQL 18.7 database; Ruff passed for the service and test.

Migration 0015 adds a per-batch idempotency key and SHA-256 request hash to batch events, a partial unique index, an immutable-event trigger, and narrowly scoped runtime grants. The service locks the batch row before checking an idempotency key. Exact retries return the original event; reusing a key with different command/notes is rejected. Status update, event insert and tenant audit event are one transaction.

Implemented commands and guards:

- `plan_batch`: requires an active recipe and recipe version.
- `start_mixing`: only from `planned`; stamps `started_at`.
- `complete_mixing`: requires posted material consumption.
- `complete_press`: requires a positive recorded good output.
- `start_inoculation`: requires every linked sterilization run to be completed and its cycle cooling complete.
- `complete_inoculation`: requires a completed variety allocation and an active incubation record.
- `mark_ready_for_kumbung`: requires an incubation record marked `ready_to_move` whose target time has arrived.
- `hold_batch` / `resume_batch`: preserve and restore the exact previous operational status.
- `cancel_batch`: only from `draft` or `planned`, and only before irreversible production records exist.

`reconcile_and_close` is deliberately not enabled until M10.1.8 provides the complete output/loss/recovery reconciliation workflow. M10.1.4 (migration 0016) is user-validated on disposable PostgreSQL 18.7: migration and smoke test passed, runtime non-owner integration test passed (1 passed) after removing an unnecessary warehouse row lock, and Ruff passed. It adds `src/app/backend/services/production_output.py`; it posts the positive sum of immutable good press quantities into a generated inventory lot and production lot, with a production-output document and append-only stock ledger movement. The batch row lock and one-per-batch `production_output_postings` record make exact retries return the original posting. Press rejects are written to `production_losses` at stage `press_baglog`. Output inventory valuation uses actual posted material-consumption cost only; machine overhead and final cost snapshots remain deferred. The caller must select an active warehouse at the batch location and authorize both production and inventory operations. Commands are service-level functions in this milestone; HTTP route and QML integration are not included.

## 7. Known schema/service gaps before lifecycle implementation

- The M10 schema initially omits `press_baglog` from the batch status constraint; migration 0012 adds it. The lifecycle service must target the post-0012 status vocabulary.
- Migration 0013 adds the shared `sterilization_cycles` parent and `sterilization_runs.cycle_id`; legacy runs intentionally remain nullable until explicitly reconciled. Migration 0017 adds explicit unit conversion master data, capacity and schedule snapshots, immutable cycle events, machine-overlap guards and per-run/per-cycle/per-batch allocation-capacity guards. `src/app/backend/services/sterilization.py` schedules one cycle across multiple active machines, splits a batch across runs, starts/completes each run and records cooling readiness only after every run's snapshotted cooling duration has elapsed. Service locks use transaction-scoped advisory locks and do not require UPDATE privilege on the sterilizer master table.
- Migration 0013 adds immutable `production_press_outputs` records with per-batch sequence uniqueness and database-enforced `processed = good + rejected` reconciliation. Migration 0014 enforces active machine status, matching production unit and matching output unit at insert time. The press-output record is not itself an inventory posting.
- Production output posting is explicitly rejected by the generic inventory posting service and needs a dedicated atomic production-output service.
- Variety-specific output lot lineage needs a clear model connecting press output, sterilization allocations, inoculation variety allocations and resulting inventory lots.
- `production_losses` supports stage and disposition, but service guards are needed to prevent over-recording and to connect loss quantities to the correct available balance.
- `kumbung_placements` is append-only, but capacity and available-lot service enforcement is still outstanding.
- The M10 architecture document points to `clients/cross-platform/src/app/backend/services/inventory.py`; the repository layout and actual file are `src/app/backend/services/inventory.py`. Correct that documentation path during the implementation pass.

## M10.1.6 inoculation allocation foundation

Migration `0018_m10_1_6_inoculation_allocations.sql` adds immutable inoculation run events, immutable variety-allocation rows, and a database capacity guard. An allocation is accepted only while the batch is in `inoculation`, the inoculation run is planned, the batch and run belong to the same production unit, the mushroom variety is active, and the quantity unit matches the batch output unit. The guard serializes allocation inserts against run completion and checks cumulative variety allocation against the quantity released by completed, cooled sterilization runs. Partial allocation is allowed; the remainder is intentionally left visible as unallocated quantity.

`src/app/backend/services/inoculation.py` provides:
- `schedule_inoculation_run`: one inoculation run may combine allocations from multiple cooled batches and assign each batch to one or more active mushroom varieties. A repeated run code with an identical allocation payload returns the existing run; a different payload is rejected.
- `complete_inoculation_run`: completes a planned run only when immutable allocation rows exist, and appends an immutable run event.
- `create_incubation_record`: creates a batch incubation timer with a caller-selected positive target duration and timezone-aware start time. It does not silently assume a 30-day duration or advance the batch state; the caller subsequently invokes the guarded `complete_inoculation` lifecycle command.

The caller remains responsible for membership authorization and transaction commit/rollback. The runtime role receives INSERT/UPDATE only on the operational run and incubation records; allocation and event history cannot be updated or deleted. Migration 0018 has a dedicated PostgreSQL smoke test. The M10.1.5 PostgreSQL integration scenario is extended to exercise variety allocation, run completion, a 32-day incubation record, and the lifecycle hand-off using the restricted runtime role.

Scope boundary: this milestone records batch-to-variety allocation lineage and configurable incubation start. It does not yet split the shared production inventory lot into separate variety-specific inventory lots or post separate variety-level inventory balances. That must be handled with the downstream inventory/traceability design rather than creating duplicate stock. The next M10.1.7 work will address incubation readiness, variety-specific lot lineage, and kumbung placement/capacity as one consistent traceability path.


## M10.1.7 — Incubation readiness and kumbung placement

Migration `0019_m10_1_7_incubation_kumbung_lineage.sql` adds append-only incubation events and variety-specific production-lot segments. A segment references one completed inoculation allocation and partitions the already-posted production lot; it does not create a second inventory lot or duplicate inventory-ledger quantity. Unallocated inoculated output remains visible as the difference between the source lot and its segments.

The incubation service records the start event. `mark_incubation_ready` requires the configured `expected_move_at` to have arrived, marks the record ready, appends an immutable event, and invokes the guarded `mark_ready_for_kumbung` batch transition in the same caller-owned transaction.

Kumbung capacity is now tied to an explicit `capacity_unit_id`. Existing kumbungs remain readable but cannot receive new placements until their capacity unit is configured. Placement and move commands:
- require a ready batch and an active kumbung at the batch's production location;
- require an exact lot-segment unit and an explicit conversion to the kumbung capacity unit when units differ;
- serialize on the kumbung and lot-segment advisory locks;
- prevent over-placement, source overdraw and negative occupancy;
- write append-only placement ledger rows with a shared reference for paired moves.

The database does not accept generic correction, harvest-removal or loss-removal placement rows. Those require explicit domain commands. The user should configure capacity units for existing kumbungs before adopting the new placement service.

## M10.1.8 — Loss, recovery, reconciliation and costing

Migration `0020_m10_1_8_loss_recovery_reconciliation.sql` adds immutable loss event history, idempotent loss request keys, source-stage quantity guards, immutable recovery posting evidence, and a batch reconciliation record. A loss is appended first and may move once from `pending` to a terminal disposition. Recovered/recycled disposition requires a full matching recovery lot and its posted inventory document/ledger entry.

Recovery creates a new inventory lot at the selected active warehouse. Its value is the sum of the salvageable historical material value and the incremental recovery/rework cost. These are separate snapshots so the example `800 + 400 = 1,200` remains auditable; master price changes do not rewrite the recovered lot valuation. Recovery uses the source lot's configured item-unit conversion and tenant base currency.

Kumbung losses reference a specific variety segment and source kumbung. They reduce calculated occupancy and remaining segment quantity without mutating the placement ledger. The `kumbung_stock` view includes those append-only losses.

Batch closure is now a guarded lifecycle command, not a direct status update. `reconcile_and_close_batch` requires:
- every non-press loss to have a terminal disposition;
- every recovered/recycled loss to have a complete posted recovery lot;
- good output quantity to equal net current kumbung placement plus post-output losses (mixing losses are tracked separately from finished baglog quantity);
- posted material consumption and machine overhead allocations to reconcile in the tenant base currency;
- an immutable final cost snapshot and an immutable reconciliation evidence row.

Press rejection remains separately traceable as a press-stage loss and is not double-counted against good output. Pre-output mixing losses remain part of batch cost/yield history but are not added to finished-baglog reconciliation quantity. Harvest losses are deliberately rejected until the M10 harvest domain exists; this milestone closes the baglog production lifecycle through kumbung placement, not the downstream mushroom-harvest lifecycle.
