# M12.1 — Mobile-First UX Architecture

**Status:** Proposed foundation  
**Visual direction:** Industrial Professional  
**Product strategy:** Mobile-first, adaptive to tablet and desktop  
**Technology:** PySide6 + Qt Quick/QML; no browser/WebView UI layer

## 1. Product experience principles

Miselium is a professional business and production application whose primary day-to-day experience must work exceptionally well on smartphones. Desktop remains a first-class productivity environment, but it must not dictate the mobile interaction model.

Design mobile-first, then progressively enhance the same product for larger screens:

1. Start with the smallest practical screen and the most common field workflows.
2. Prioritize operational clarity, short task completion, and touch ergonomics.
3. Keep navigation and actions predictable across device sizes.
4. Increase information density and expose additional workspace tools as screen space grows.
5. Share domain behavior, validation, permissions, and design semantics; adapt layout and interaction patterns per platform.

Mobile-first does **not** mean scaling a phone layout up to desktop. Desktop-first does **not** mean squeezing a desktop sidebar and data grid onto a phone. Each form factor gets an intentional presentation.

Avoid marketing-style hero sections, decorative oversized cards, excessive rounded surfaces, and large empty gutters in operational screens. Use cards only when they communicate a meaningful grouping or summary.

## 2. Smartphone experience

The smartphone experience is the baseline for task design and responsive behavior.

### Mobile application shell

- **Top app bar:** current page title, back navigation when needed, and a small number of contextual actions.
- **Primary navigation:** bottom navigation for a small set of high-frequency destinations. Less frequent modules live in a clearly grouped More/Modules destination or a navigation drawer.
- **Workspace:** single-column content, touch-friendly controls, clear section hierarchy, and minimal horizontal scrolling.
- **Task actions:** prominent primary action in a predictable location; avoid placing critical actions in tiny icon-only controls.
- **Feedback:** visible inline validation, concise toast/snackbar feedback, progress and sync status without interrupting the task.

### Mobile interaction patterns

- Forms use a single-column flow, sensible keyboard/input types, large touch targets, and explicit save/cancel behavior.
- Long forms are divided into meaningful steps or sections; preserve entered data when navigating within a workflow.
- Operational records appear as readable list rows or compact summaries. Open a dedicated detail view for full information.
- Tables transform into stacked records, key-value summaries, or horizontally scrollable grids only when comparison truly requires columns.
- Filters open as a bottom sheet or dedicated filter screen; applied filters remain visible and easy to clear.
- Use bottom sheets for short contextual choices, not as a substitute for every full-page workflow.
- Support camera, barcode/scanner, and device capabilities through platform-specific adapters where available.
- Critical tasks must remain usable with one hand where practical; primary actions should be reachable and not conflict with system gesture areas.

### Example mobile information architecture

The final destinations should be validated against actual tenant roles and enabled modules. A starting model:

- Beranda
- Operasional (production, inventory, purchasing/sales where enabled)
- Aktivitas / Tasks
- Laporan
- Lainnya (master data, settings, less frequent tools)

Do not expose modules that the active tenant is not entitled to use. Platform-level and tenant-level settings remain separate scopes.

## 3. Tablet and desktop experience

As available width grows, the application progressively reveals more workspace structure and supports more simultaneous information.

### Tablet

- Navigation rail or collapsible sidebar.
- Contextual top toolbar.
- Two-pane layouts for list/detail where useful.
- Larger form layouts may use two columns when the task benefits from it.
- Touch targets remain comfortable; do not blindly switch to dense desktop controls.

### Desktop

The desktop experience should feel familiar to users of established office, accounting, and ERP software.

- **Application navigation:** persistent left sidebar with grouped modules, selected location, and collapsible state.
- **Context toolbar:** page title, breadcrumb/context, primary and secondary actions, search/filter controls when relevant.
- **Workspace:** operational tables, split panes, forms, and detail/inspector panels.
- **Status bar:** connection/synchronization state, active tenant/location where applicable, background task state, and application version.
- Keyboard shortcuts, context menus, multi-selection, and efficient keyboard focus order for frequent workflows.

Dialogs and drawers are reserved for focused tasks. Do not turn every page into a modal. Long-running or multi-step workflows should have a dedicated workspace.

## 4. Industrial Professional visual language

The Industrial Professional direction should communicate familiarity, reliability, and operational focus—like established office software, not a consumer social app.

- Neutral, restrained surfaces inspired by professional office software.
- Clear borders and alignment instead of floating, heavily rounded cards.
- Comfortable touch density on mobile; compact and comfortable density options on desktop.
- Strong typography hierarchy with readable labels and numeric values.
- Color is semantic: accent, success, warning, danger, and information.
- Icons support recognition but never replace clear labels for primary navigation.
- Consistent control states: default, hover (where applicable), pressed, focused, disabled, loading, and invalid.

### Initial palette direction

Values are starting tokens, not final brand commitments. Review them in M12.2 prototypes on both phone and desktop.

| Token | Light direction | Dark direction |
|---|---|---|
| App background | Neutral light gray | Deep neutral charcoal |
| Workspace surface | White / near-white | Elevated charcoal |
| Secondary surface | Light gray | Dark slate |
| Primary text | Near-black | Near-white |
| Secondary text | Neutral gray | Muted gray |
| Border | Mid-light gray | Dark gray |
| Accent | Professional blue | Accessible blue |
| Success | Restrained green | Accessible green |
| Warning | Amber | Accessible amber |
| Danger | Restrained red | Accessible red |

Do not use bright green as a general brand accent. Reserve semantic colors for statuses and feedback.

## 5. Theme and presentation preferences

Theme is a first-class user preference, not page-level styling.

Initial modes:

- **Light**
- **Dark**
- **System** (follow OS preference when the platform exposes a reliable preference)

Initial presentation preferences:

- Theme: System / Light / Dark.
- Density: Comfortable / Compact on desktop; touch-optimized sizing on mobile.
- Navigation: expanded/collapsed on desktop; mobile navigation pattern is selected automatically.
- Optional accent customization can be considered later, with accessible contrast constraints.

Theme must be consistent across smartphone, tablet, and desktop. The same semantic token names resolve to form-factor-appropriate values. Theme and density must not alter permissions, data visibility, business rules, or workflow behavior.

### Required design layers

1. **Design tokens:** semantic colors, typography, spacing, dimensions, radii, borders, elevations, and control sizes.
2. **Theme controller:** exposes active mode and resolved token values to QML.
3. **Adaptive presentation layer:** selects layout/navigation patterns from available width and platform capabilities, not from business logic.
4. **Reusable components:** consume tokens; pages must not hard-code theme colors or dimensions.
5. **Preference persistence:** use the existing settings service after repository review; choose an appropriate platform-aware persistence mechanism.
6. **System theme adapter:** resolve System mode and update when OS preference changes where supported.

Theme changes should apply at runtime wherever Qt controls and custom components permit it. Isolate platform limitations in platform adapters.

## 6. Qt Quick implementation direction

- Retain PySide6 and Qt Quick/QML. Do not introduce a browser/WebView layer.
- Evaluate Qt Quick Controls Fusion as a neutral desktop baseline; evaluate mobile-appropriate Qt Quick Controls presentation separately.
- Build Miselium's own tokens and reusable QML components above Qt controls. Do not rely on one built-in style to provide the complete product identity across every platform.
- Centralize tokens and shared controls. Pages compose shared components rather than reimplement colors, spacing, and states.
- Keep business logic and persistence out of QML presentation components.
- Use adaptive shells and platform adapters for device-specific behavior.
- Confirm the exact supported Qt/PySide6 version and available styles before selecting controls or APIs.

## 7. Reusable component inventory

M12.2–M12.4 should define and implement:

- Shell: mobile app bar, bottom navigation, navigation drawer, tablet navigation rail, desktop sidebar, contextual toolbar, breadcrumb, status bar.
- Data: mobile record list, record summary/detail, desktop data table, sortable header, filter row, pagination, empty/loading states.
- Forms: field wrapper, text/number/date input, select, checkbox, radio, validation message, step/progress indicator.
- Actions: primary/secondary/quiet buttons, split button (desktop where suitable), command/menu item, contextual action sheet.
- Feedback: toast/snackbar, inline alert, progress indicator, confirmation dialog.
- Layout: section header, adaptive split pane, inspector/detail panel, bottom sheet, responsive breakpoint helpers.

Components must expose predictable properties and accessible names, support keyboard focus on desktop, and provide visible focus/pressed/disabled/error states. Interactive controls must have touch-friendly hit areas on mobile.

## 8. Responsive behavior and breakpoints

Breakpoints are a presentation decision and should be based on usable window width, not assumptions about device model. Initial bands for prototyping:

- **Compact:** phone-sized single-column workspace and bottom navigation.
- **Medium:** tablet/navigation rail and optional two-pane content.
- **Expanded:** desktop sidebar, toolbar, status bar, and multi-pane workspace.

Exact breakpoint values and transitions must be measured and validated in M12.2 prototypes. Support window resizing and orientation changes without losing form state or context.

## 9. M12.1 deliverables and acceptance criteria

M12.1 is complete when:

- Mobile-first product principles and smartphone shell are documented.
- Tablet and desktop adaptive patterns are documented separately.
- Navigation groups and module entitlement behavior are defined.
- Industrial Professional design principles and semantic color roles are agreed.
- Light, Dark, and System modes are specified across form factors.
- Theme token/controller/adaptive-presentation responsibilities are defined.
- Mobile, tablet, and desktop component inventories are agreed.
- The component inventory and implementation sequence are agreed.
- No business workflow, database schema, or backend behavior is changed by this architecture milestone.

## 10. Recommended implementation sequence

1. M12.1: approve this mobile-first UX architecture.
2. M12.2: build paired smartphone and desktop visual prototypes for the same representative workflow (Settings or Inventory), then validate tablet adaptation.
3. M12.3: implement adaptive application shells and theme controller.
4. M12.4: implement shared controls, mobile record patterns, and desktop data components.
5. M12.5: migrate Settings into an adaptive workspace.
6. M12.6: validate on Android, Windows, and Linux, including touch, keyboard, resizing, and theme behavior.

## 11. Current repository observations

The current QML shell uses a horizontal `TabBar` in `src/app/ui/Main.qml`. Dashboard and Settings pages contain page-local hard-coded dark colors and card/grid layouts. This explains the current visual direction, but does not imply the application should become desktop-first.

M12 should replace page-local visual decisions incrementally through shared tokens, adaptive shells, and reusable components. Existing application services and backend behavior should remain intact.
