# M12.1 — Desktop UX Architecture

**Status:** Proposed foundation  
**Visual direction:** Industrial Professional  
**Target:** PySide6 + Qt Quick/QML desktop first, adaptive presentation for Android

## 1. Product experience principles

Miselium is a professional business and operations application. Its desktop experience should feel familiar to users of established office, accounting, and ERP software rather than resemble a responsive SaaS website.

Priorities, in order:

1. Operational clarity and predictable interaction.
2. Information density without visual clutter.
3. Consistent navigation and keyboard-friendly workflows.
4. Clear hierarchy between navigation, commands, work area, and system status.
5. Adaptable presentation across desktop and mobile without forcing identical layouts.

Avoid decorative oversized cards, excessive rounded surfaces, marketing-style hero sections, and large empty gutters in operational screens. Use cards only when they communicate a meaningful grouping or summary.

## 2. Desktop application shell

The desktop shell is composed of four persistent regions:

- **Application navigation:** permanent left sidebar with grouped modules, current location, and collapsible state.
- **Context toolbar:** page title, breadcrumb/context, primary and secondary actions, search/filter controls when relevant.
- **Workspace:** page content. Operational pages should prioritize tables, split panes, forms, and detail panels over card grids.
- **Status bar:** connection/synchronization state, active tenant/location where applicable, background task state, and application version.

Dialogs and drawers are reserved for focused tasks. Do not turn every page into a modal. Long-running or multi-step workflows should have a dedicated workspace.

### Proposed desktop navigation groups

The exact modules remain entitlement-driven and configurable. Initial information architecture:

- Overview
- Operations
  - Production
  - Inventory
  - Purchasing
  - Sales
- Master Data
- Reports
- Settings

The navigation must not expose modules that the active tenant is not entitled to use. Platform-level and tenant-level settings remain separate scopes.

## 3. Industrial Professional visual language

### Visual characteristics

- Neutral, restrained surfaces inspired by professional office software.
- Clear borders and alignment instead of floating, heavily rounded cards.
- Compact-to-comfortable density options for data-heavy work.
- Strong typography hierarchy with readable labels and numeric values.
- Color is semantic: accent, success, warning, danger, and information.
- Icons support recognition but never replace clear labels for primary navigation.

### Initial palette direction

The values below are starting tokens, not final brand commitments. They must be reviewed in the M12.2 visual prototype.

| Token | Light direction | Dark direction |
|---|---|---|
| App background | Warm/cool neutral gray | Deep neutral charcoal |
| Workspace surface | White / near-white | Elevated charcoal |
| Secondary surface | Light gray | Dark slate |
| Primary text | Near-black | Near-white |
| Secondary text | Neutral gray | Muted gray |
| Border | Mid-light gray | Dark gray |
| Accent | Professional blue | Accessible blue |
| Success | Restrained green | Accessible green |
| Warning | Amber | Accessible amber |
| Danger | Restrained red | Accessible red |

Do not use bright green as a general brand accent. Reserve semantic colors for statuses and feedback.

## 4. Theme architecture

Theme is a first-class application preference, not page-level styling.

Initial user-selectable modes:

- **Light**
- **Dark**
- **System** (follow the operating system when the platform exposes a reliable preference)

The architecture must allow future tenant or organization branding without coupling it to business logic.

### Required design layers

1. **Design tokens:** colors, typography, spacing, dimensions, radii, borders, elevations, and control sizes.
2. **Theme controller:** exposes the active mode and resolved token values to QML.
3. **Reusable components:** consume tokens; pages must not hard-code theme colors or dimensions.
4. **Preference persistence:** store the user's theme and density preferences using the desktop application's settings mechanism (QSettings or the existing settings service after repository review).
5. **System theme adapter:** resolve System mode and update the theme when the OS preference changes where supported.

Theme changes should apply at runtime without restarting the application wherever Qt controls and custom components permit it. If a specific platform style requires initialization-time selection, keep that limitation isolated in the platform adapter.

### Initial theme preferences

- Theme: System / Light / Dark
- Density: Comfortable / Compact
- Sidebar: Expanded / Collapsed (desktop only)

Theme and density are presentation preferences. They must not alter permissions, data visibility, business rules, or workflow behavior.

## 5. Qt Quick implementation direction

- Retain PySide6 and Qt Quick/QML. Do not introduce a browser/WebView layer.
- Evaluate Qt Quick Controls Fusion as a neutral desktop baseline; apply Miselium's own tokens and reusable QML components above it.
- Do not rely on a single built-in style to provide the complete product identity.
- Centralize tokens and shared controls. Pages should compose shared components rather than reimplement colors, spacing, and control states.
- Keep business logic and persistence out of QML presentation components.
- Use platform adapters for desktop-specific behavior and a separate adaptive shell/presentation strategy for Android.

## 6. Reusable component inventory

M12.2–M12.4 should define and implement at least:

- Shell: sidebar, navigation group/item, toolbar, breadcrumb, status bar, workspace tabs.
- Data: data table, sortable header, filter row, pagination, empty state, loading state.
- Forms: field wrapper, text/number/date input, select, checkbox, radio, validation message.
- Actions: primary/secondary/quiet buttons, split button, command/menu item.
- Feedback: toast, inline alert, progress indicator, confirmation dialog.
- Layout: section header, split pane, inspector/detail panel, responsive breakpoint helpers.

Components must expose predictable properties and accessible names, support keyboard focus, and provide visible hover/focus/disabled/error states.

## 7. Responsive and cross-platform behavior

Desktop and Android share domain services, design tokens where appropriate, and component semantics, but not necessarily the same shell.

- Desktop: persistent sidebar, context toolbar, workspace, status bar, keyboard shortcuts, context menus.
- Android: mobile navigation pattern, touch-sized controls, simplified toolbar, mobile-friendly forms and lists.
- Avoid hard-coding desktop dimensions into shared business pages.
- Preserve the same permissions, validation, and business workflows across platforms.

## 8. M12.1 deliverables and acceptance criteria

M12.1 is complete when:

- The application shell and navigation regions are documented.
- Navigation groups and module entitlement behavior are defined.
- Industrial Professional design principles and semantic color roles are agreed.
- Light, Dark, and System modes are specified.
- Theme token/controller/component responsibilities are defined.
- Desktop versus Android presentation responsibilities are documented.
- The component inventory and implementation sequence are agreed.
- No business workflow, database schema, or backend behavior is changed by this architecture milestone.

## 9. Recommended implementation sequence

1. M12.1: approve this UX architecture.
2. M12.2: build a visual design system and a representative desktop prototype (Settings or Inventory).
3. M12.3: implement the application shell and theme controller.
4. M12.4: implement shared controls and data components.
5. M12.5: migrate Settings into a true workspace.
6. M12.6: validate/adapt presentation for Windows, Linux, and Android.

## 10. Current repository observations

The current QML shell uses a horizontal `TabBar` in `src/app/ui/Main.qml`. Dashboard and Settings pages contain page-local hard-coded dark colors and card/grid layouts. This is the main reason the current UI reads more like a web dashboard than a desktop business application.

M12 should replace these page-local visual decisions incrementally through a shared shell and design system. Existing application services and backend behavior should remain intact.
